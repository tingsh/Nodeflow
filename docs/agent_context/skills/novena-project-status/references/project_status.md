# Novena Project Status

## Current Stage
- Phase: Pre-Launch / Release Candidate.
- Status: Core Hub and Gateway capability is largely built, and recent Gateway work materially improves appliance operability. An 18 July cross-repository audit nevertheless found P0 gaps in offline-at-claim activation, inbound MQTT identity, HTMX tenant scoping, OTA trust/input handling, and reproducible release assets. The product is suitable for internal replay after fixes, but the 20-customer handout is on hold until the code/security gate and a 3-5 customer technical canary pass.

## Current Sprint Goal
Close cross-system pilot blockers, commit a reproducible Hub/Gateway release, complete current three-vertical CM4 hardware replays, and qualify a 3-5 customer technical canary before wider rollout.

## What Is Built
- Novena Hub: multi-tenant Django SaaS, teams and RBAC, onboarding, devices, sites, gateways, telemetry ingestion, TimescaleDB storage, Redis and Celery buffering, WebSockets, dashboard widgets, alerts, automations, maintenance tickets, Wagtail marketing content, Stripe billing foundations, and AI insights.
- Novena Gateway: Python gateway daemon, Modbus connector support, remote config handling, RPC, attribute sync, payload formatting, offline buffering, discovery, logging, network watchdog, and service/install files.
- Local development: WSL-native Hub stack is the preferred path with PostgreSQL and TimescaleDB, Redis, Mosquitto, Django, Celery worker, Celery Beat, MQTT consumer, and Vite.

## High-Priority Roadmap
1. Pilot security/integrity: durable Gateway activation retry/ack, serial-scoped MQTT identity, tenant-scoped mutation paths, exact device identity, recoverable telemetry queueing, and safe OTA disablement/signing.
2. Reproducible appliance release: commit the latest Gateway/Hub deployment work, align Mosquitto bootstrap/provisioning assets, run dependency-complete tests, build clean artifacts, and complete 24-48 hour CM4 burn-in.
3. Customer proof: pass energy, cold-chain, and facilities hardware replays, then a 3-5 customer canary before the planned 20-customer cohort.
4. Commercial proof: measure time to first data, support cost, telemetry coverage, action/use, willingness to pay, and conversion; keep energy as the lead hypothesis.
5. Paid operations: enable secure Stripe webhooks/live billing, secure inbound WhatsApp mutations, finish customer/installer docs, and polish mobile/tablet field workflows.
